# Shared account Passkeys

Account sign-in and Secure Chat use the same `chat_passkeys` credentials. The profile lists account Passkeys without separate login/chat purpose labels. An email login request sends its verification code immediately; Passkey sign-in is an independent action that obtains a fresh challenge for the current email and shows its progress and failures.

WebAuthn signatures authenticate account sign-in. Secure Chat also needs a local PRF result to decrypt its account vault. PRF output and private chat keys stay in the browser; credential serialization sends only extension support information. A successful email or Google login resolves the existing account rather than creating another chat identity.

Each retained chat identity has its original immutable record in `chat_account_vault_versions`. Additional Passkeys receive immutable encrypted copies of the same identity in `chat_account_vault_wrappers`, keyed by account, identity version and credential. Enrollment decrypts the existing identity locally, wraps its original root/encryption/signing keys with the selected Passkey's PRF result, and signs the wrapper with the original identity. The server verifies both the selected credential proof and the identity signature before adding the wrapper. It does not replace account keys, the current identity head, original vaults or message history.

Adding a Passkey from the profile redirects an account with existing chat keys to `pages/chat.html?passkeys=add`. An older account Passkey with missing wrappers has a **Sync chat access** action that opens `pages/chat.html?passkey=<credentialId>`. The user unlocks existing Secure Chat before continuing. Enrollment includes every retained identity version; older versions can require another existing Passkey. Cancelling or retrying preserves the original identity and any wrappers already added. A newly registered credential remains selected for retry rather than creating another one.

Passkey enrollment remains in account settings. The normal Chat profile does not offer an Add Passkey button. Friend connections use chat user ID search; invitation links and tokens are retired, and their former API routes return `410 CHAT_INVITES_REMOVED` to authenticated requests. Existing contacts and conversations remain intact. Migration `0024_retired_invites_cleanup.sql` removes the obsolete invitation table; the retired routes no longer depend on it.

After the first successful unlock, the browser reuses access within the same login session, including reloads, navigation back to Chat and another tab. The encryption Worker seals the current and retained identity keys with a non-extractable local AES-GCM key. IndexedDB stores that key and the encrypted snapshot, bound to the account, exact login token and expiry. PRF output and plaintext private keys are never written to browser storage. Restore first checks authenticated server state, retained public identities and the originating Passkey's availability; a changed identity or unavailable credential requires another unlock.

Sign out, account switching, expired or rejected authentication and explicit local clearing invalidate this cache and lock open Chat pages. Cross-tab notifications are scoped to the old login so delayed work cannot clear a newer login. Missing or unavailable browser storage falls back to the ordinary Passkey unlock. A new browser or a new login must unlock once before it can reuse access.

Vaults predating credential attribution can have a null original credential ID. Their wrappers are marked `legacyCandidate`, which permits trying an existing credential but does not claim it can decrypt the vault. Enrollment must explicitly rewrap these identities. An inaccessible historical candidate must not prevent access to a correctly unlocked current identity; the page offers synchronization of older history. It must never initialize a replacement identity to bypass a missing key.

Revocation checks every retained identity version atomically. At least one active credential must remain for sign-in, and every retained vault that the removed credential can open must retain another confirmed active wrapper. Directory, contact and public discussion readiness use these wrappers as well as the original credential, so safely retiring an original Passkey does not disable the account's chat access.

Migration `0023_shared_passkey_vault_wrapping.sql` adds a challenge operation scope and fills missing original wrappers with `INSERT OR IGNORE`. The `account-wrap` operation proof cannot initialize or reset an identity; this server-side operation scope is independent of the shared credential's user-facing capabilities. Apply the migration before deploying the Worker and versioned static assets. Do not reset client storage or delete old Passkeys to repair enrollment.

Validation includes the Google-to-email account-preservation test, authenticated wrapper and revocation tests, fresh-worker decryption of current and historical messages using a new Passkey, and real rendered login/settings/chat flows. `npm run check` covers server and crypto contracts. Run `npm run test:login-browser` for the login/settings interactions and `npm run test:chat-browser` for the integrated Secure Chat flow. Browser tests use isolated accounts and replace physical authenticator interaction; the login test also exercises Chromium's native WebAuthn API with a virtual authenticator. They do not send real email or change production accounts.
